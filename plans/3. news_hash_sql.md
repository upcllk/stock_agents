可以，基于你现在这几张表，建议不要推倒重来，而是做 **“最小侵入式扩展”**：

核心思路是把流程拆成这几层：

1. **原始新闻入库**
2. **文本去重 / 近重复检测**
3. **新闻聚类**
4. **事件归并**
5. **LLM 总结**
6. **投资信号提取**

这样你的系统就不会变成“每条新闻都直接喂给 LLM”，而是先做一轮工程化收敛，再把更干净、更有价值的数据送给大模型。

# Agent1 技术方案（基于现有表扩展）

## 1. 目标

当前场景：

* 你输入公司名称
* 调用大模型联网搜索，返回近 N 篇新闻稿
* 再调用另一个大模型对新闻做总结
* 最终落库

现在要在这个流程中加入：

* 文本去重
* 新闻聚类
* 事件归并
* LLM 总结
* 投资信号提取

目标是实现一个工程上可落地的 Agent1 MVP：

* 避免重复新闻反复喂给 LLM，降低成本
* 将同一事件的多篇新闻合并，提高信息密度
* 保留原始新闻、聚类结果、事件结果，便于回溯
* 后续可逐步扩展为更强的投资决策辅助系统

---

## 2. 总体架构

推荐处理链路如下：

```text
公司列表
  -> 调用联网 LLM 搜索新闻
  -> 原始新闻标准化
  -> 精确去重（url/title/source）
  -> 近重复去重（SimHash）
  -> 新闻聚类（同一主题）
  -> 事件归并（同一事件）
  -> LLM 生成事件级总结
  -> LLM 提取投资信号
  -> 落库
```

其中关键原则是：

* **去重要放在 LLM 总结之前**
* **聚类 / 事件归并 也尽量放在 LLM 总结之前**
* **LLM 不处理“每条新闻”，而处理“清洗后的一组代表新闻 / 一个事件簇”**

这样最省钱，也最稳。

---

## 3. 对现有表的评估

你现有的表：

* `company_watchlist`：保留
* `news_event`：适合继续作为“新闻主表”
* `event_analysis`：适合继续作为“分析结果表”
* `news_hash`：目前只支持简单 hash 去重，不够用，需要扩展

### 当前不足

#### 3.1 `news_event` 信息不够

目前只有：

* 标题
* 来源
* url
* 发布时间
* raw_summary

但你后续要做近重复检测、聚类、事件归并，至少还需要：

* 原始正文 / 原始片段
* 清洗后的文本
* simhash
* 去重状态
* 聚类ID
* 事件ID

#### 3.2 `news_hash` 只能做精确去重

你现在的 `hash = sha256(title + source)` 只能挡住“完全一样”的新闻，挡不住：

* 标题略改
* 同一稿件不同媒体搬运
* 同一篇稿件中多了广告、免责声明、引用段落

#### 3.3 `event_analysis` 现在是“按单条新闻分析”

但更合理的是：

* 单条新闻可以有分析
* 更重要的是“事件级分析”

因为投资上真正关心的是事件，不是某一篇稿子。

# 5. 去重方案设计

## 5.1 去重位置

你的场景里，**去重必须放在第二个 LLM 解析之前**。

流程应为：

```text
联网搜索返回新闻
 -> 原始新闻标准化
 -> 去重
 -> 聚类 / 事件归并
 -> 再送 LLM 总结
 -> 落 event_analysis
```

### 原因

#### 1）省大模型成本

重复新闻没必要反复总结。

#### 2）减少污染

如果同一事件的 10 篇搬运稿全部喂给 LLM，模型会把“重复出现”误当成“事件更重要”。

#### 3）利于后续聚类

只有先做去重，后面的主题聚类和事件归并才不会被水稿干扰。

---

## 5.2 去重分两层

### 第一层：精确去重

规则：

* `url` 完全相同
* `sha256(cleaned_text)` 相同
* `sha256(normalized_title + source)` 相同

### 第二层：近重复去重

用 SimHash：

* 对 `cleaned_text` 生成 64 位 SimHash
* 与最近一段时间、同一 ticker 的新闻做比较
* 汉明距离小于等于某个阈值，则判定为近重复

### 推荐阈值

64 位 SimHash 常见经验：

* `distance <= 3`：高度近似
* `distance <= 5`：可认为相似搬运稿
* `distance > 5`：通常差异已较明显

MVP 推荐先用：

```text
distance <= 3 -> near_duplicate
distance 4~5 -> suspicious，视业务决定
distance > 5 -> unique
```

---

## 5.3 文本清洗规则

SimHash 效果强依赖文本清洗。
新闻正文建议做这些清洗：

### 基础清洗

* 转小写
* 去 HTML 标签
* 去多余空白符
* 去换行、制表符
* 去掉统一免责声明
* 去掉“来源：xxx”“责任编辑：xxx”
* 去掉“点击查看原文”“免责声明：本文不构成投资建议”等模板话术

### 业务清洗

* 去掉发布时间、作者名
* 去掉转载声明
* 去掉固定页脚
* 去掉股票代码括号附注
* URL、邮箱、电话号码统一替换成占位符

### 长度控制

* 如果正文特别长，只取：

  * 标题
  * 导语
  * 前 500~1000 字正文

因为新闻搬运稿的核心差异通常也集中在这些部分。

---

## 5.4 去重输出策略

对每条新闻判定后，写入：

* `duplicate_status`
* `duplicate_of`
* `simhash`

其中：

* `unique`：进入后续聚类
* `exact_duplicate / near_duplicate`：保留原始记录，但不再进入 LLM 总结主流程

这样好处是：

* 数据不丢
* 可审计
* 后续可以分析“媒体转载热度”

---

# 6. 新闻聚类方案

## 6.1 聚类目标

去重后，剩下的新闻仍然可能很多。
例如同一公司同一天有：

* 财报新闻
* 财报解读
* 分析师点评
* 电话会纪要

这些不一定是重复，但属于同一主题。

所以需要 `news_cluster`。

---

## 6.2 MVP 聚类规则

MVP 不要一上来搞复杂向量聚类，先用规则法：

### 聚类维度

* 同一 `ticker`
* 发布时间窗口相近（如 3 天内）
* 标题关键词相似
* 正文 SimHash 接近，或者标题 token overlap 高

### 可以做一个简单打分：

```text
cluster_score =
  标题相似度 * 0.5
+ 正文相似度 * 0.3
+ 发布时间接近度 * 0.2
```

当分数超过阈值时，归入同一个 cluster。

### 主题标签

先用规则分类：

* earnings
* guidance
* product
* partnership
* acquisition
* lawsuit
* regulation
* management
* risk
* other

这个标签既可以由规则打，也可以在后面让 LLM 修正。

---

# 7. 事件归并方案

## 7.1 cluster 和 event 的区别

### cluster

偏“文本主题相似”

### event

偏“投资上属于同一件事”

比如：

* “苹果发布 Q1 财报”
* “苹果 CEO 电话会强调 AI 战略”
* “多家投行上调苹果目标价”

这几个文本未必很像，但投资上可能属于同一事件链。

---

## 7.2 MVP 事件归并规则

建议按以下规则先做：

### 归并条件

* 同一 `ticker`
* 同一 `event_type`
* 时间窗口内（比如 3~7 天）
* cluster 主题接近

### 结果

若满足条件，则归入同一个 `event_group`

### 代表新闻

从 event 内选择一条 `representative_news_id`，规则可以是：

* 官方来源优先
* 原始来源优先
* 发布时间最早优先
* 正文最长优先

---

# 8. LLM 总结与投资信号提取

## 8.1 LLM 放在哪一层

推荐两层：

### 第一层：事件级总结

输入不是单条新闻，而是：

* event 下若干条代表新闻
* 或 cluster 下去重后的几条代表新闻

输出：

* 事件摘要
* 事件类型
* 对公司影响方向
* 影响周期
* 可信度

### 第二层：投资信号提取

基于事件总结再提一层：

* 是否利多 / 利空 / 中性
* 是短期扰动还是中长期变化
* 是否需要加入观察清单
* 信号强度

---

## 8.2 为什么不要“每条新闻直接总结”

因为那样会有几个问题：

* 重复稿浪费 token
* 事件上下文被割裂
* 最终数据库里会存大量碎片化结论

更好的方式是：

**新闻是原材料，事件才是分析单位。**

---

## 8.3 `event_analysis` 的使用建议

推荐一个 event 对应至少一条 event 级分析记录：

```text
summary_level = 'event'
event_id = xxx
news_id = representative_news_id
```

如果你还想保留单条新闻分析，也可以有：

```text
summary_level = 'news'
news_id = xxx
```

但 MVP 阶段建议以 `event` 为主。

---

# 9. 推荐处理流程

## 9.1 单次任务流程

### Step 1：抓取新闻

针对 `company_watchlist` 中启用的公司，调用联网 LLM，拉取最近 N 篇新闻。

落库：

* 先写 `fetch_batch`
* 再写 `news_event`

### Step 2：标准化与清洗

对每条新闻生成：

* `content_text`
* `cleaned_text`
* `content_length`
* `title_hash`
* `exact_hash`
* `simhash`

### Step 3：精确去重

检查：

* url 是否已存在
* exact_hash 是否已存在
* title_hash + source 是否已存在

命中则：

* `duplicate_status = exact_duplicate`

### Step 4：近重复去重

对未命中精确去重的新闻，和最近窗口内同 ticker 新闻比较 SimHash：

* 命中则 `near_duplicate`
* 否则 `unique`

### Step 5：新闻聚类

仅对 `unique` 新闻做 cluster 分配：

* 找已有 cluster
* 若无则新建 cluster

### Step 6：事件归并

将 cluster 归入 `event_group`：

* 找已有 event
* 若无则新建 event

同时写 `event_news_mapping`

### Step 7：LLM 事件级总结

对每个新增或更新的 event：

* 取代表新闻 + 若干补充新闻
* 调用 LLM 生成事件摘要与投资分析

写入：

* `event_group.summary_text`
* `event_analysis`

### Step 8：统计与收尾

更新 `fetch_batch`：

* 抓取数
* 唯一新闻数
* 重复数
* cluster 数
* event 数

---

# 10. MVP 推荐实现策略

## 10.1 先不要上 embedding

你这个场景第一版完全没必要先搞向量库。
建议顺序：

### 第一阶段

* 精确去重
* SimHash 近重复
* 规则聚类
* 规则事件归并
* LLM 事件总结

### 第二阶段

再考虑：

* embedding 相似度
* 向量检索
* 跨时间事件追踪
* 多公司联动事件分析

---

## 10.2 SimHash 怎么落地

Python 侧推荐：

* 自己写清洗函数
* 用 `simhash` 库，或者自己实现 64 位 SimHash
* PostgreSQL 里存 `BIGINT`

对比时：

* 拉取同 ticker 最近 7~30 天的新闻 simhash
* 计算汉明距离
* 找最小距离

# 12. 最终推荐结论

对于你这个场景，最合适的路线不是“抓一条总结一条”，而是：

```text
抓取
-> 清洗
-> 去重（精确 + SimHash）
-> 聚类
-> 事件归并
-> 事件级 LLM 总结
-> 投资信号提取
-> 落库
```

也就是说：

* **去重放在 LLM 总结前**
* **聚类、事件归并也尽量放在 LLM 前**
* **分析单位以 event 为主，而不是单条新闻**

这是最省钱、最稳、最容易扩展的做法。
