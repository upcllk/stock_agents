# 基于 LLM 联网搜索的公司新闻采集、去重、聚类、事件归并与投资信号提取技术方案

## 1. 背景与目标

当前系统面向指定公司，基于大模型的联网搜索能力抓取相关新闻稿，并通过大模型完成新闻摘要与结构化分析。由于联网搜索返回的新闻存在大量转载、搬运、引用和同一事件的多篇报道，如果直接逐条总结并入库，会带来以下问题：

* 重复新闻过多，浪费大模型调用成本
* 同一事件被重复总结，数据库信息冗余
* 投资判断被同一事件重复放大
* 后续分析、看板、告警容易失真

因此需要构建一套完整的新闻处理链路，在 LLM 总结之前增加：

* 文本去重
* 新闻聚类
* 事件归并

并在此基础上完成：

* 事件级摘要生成
* 投资信号提取
* 结构化落库

目标是形成一个可迭代扩展的新闻分析系统，为后续投资研究、舆情监控、事件追踪提供数据基础。

---

## 2. 总体方案

整体流程建议如下：

```text
输入公司名称
    ↓
调用 LLM 联网搜索
    ↓
返回新闻列表（标题、摘要、正文/正文片段、来源、时间、URL）
    ↓
原始新闻标准化
    ↓
文本清洗
    ↓
新闻去重（标题规则 + SimHash）
    ↓
新闻聚类
    ↓
事件归并
    ↓
事件级 LLM 总结
    ↓
投资信号提取
    ↓
结构化落库
```

整体设计原则如下：

1. **去重必须放在 LLM 总结之前**，优先节省模型调用成本
2. **聚类与事件归并基于去重后的新闻进行**
3. **总结尽量做成事件级总结，而不是逐条新闻总结**
4. **投资信号提取基于事件级信息生成**
5. 第一版优先可落地，后续再增强语义能力和多源融合能力

## 3. 系统分层设计

系统建议拆成以下几个模块：

### 3.1 数据采集层

职责：

* 接收输入公司名
* 调用 LLM 联网搜索
* 获取新闻列表
* 标准化搜索结果字段

输入：

* 公司名称
* 搜索时间范围
* 搜索条数上限

输出：

* 新闻原始记录列表

建议字段：

```json
{
  "company_name": "Apple",
  "title": "Apple launches new chip",
  "content": "full text or text snippet",
  "source": "Reuters",
  "publish_time": "2026-03-14T10:00:00Z",
  "url": "https://xxx.com/news/123",
  "search_time": "2026-03-14T12:00:00Z"
}
```

---

### 3.2 预处理层

职责：

* 统一字段格式
* 文本清洗
* 正文标准化
* 补充辅助特征字段

输出内容：

* `clean_title`
* `clean_content`
* `content_length`
* `source_domain`
* `fingerprint_source_text`

其中：

* `fingerprint_source_text` 用于去重
* 推荐优先使用 `title + content` 拼接文本作为去重输入

---

### 3.3 去重层

职责：

* 过滤重复新闻
* 避免转载和轻微改写新闻重复进入后续链路

建议采用两级去重：

#### 一级：标题规则去重

适合处理：

* 标题完全一致
* 标题仅差少量标点、大小写、空格

建议规则：

* 标题标准化后做完全匹配
* URL 去参数后做精确匹配
* 同源站点相同标题优先判定重复

#### 二级：正文 SimHash 去重

适合处理：

* 正文高度相似的转载
* 插入少量引用或背景介绍的搬运稿
* 标题不同但正文相似的稿件

判定逻辑建议：

* 清洗后的 `title + content` 计算 SimHash
* 与近 7 天或近 15 天历史新闻比较
* `Hamming Distance <= 3` 判定为重复
* `Hamming Distance <= 5` 可标记为疑似重复

第一版建议直接用：

```text
distance <= 3 视为重复
distance > 3 视为非重复
```

---

### 3.4 聚类层

职责：

* 将多个相似新闻聚合为一个新闻簇
* 为后续事件归并提供候选集合

这里的聚类对象不是“完全重复新闻”，而是“描述同一主题或同一件事的多篇报道”。

第一版建议使用轻量规则聚类，不必一开始就上 embedding。

推荐聚类依据：

* 公司名
* 时间窗口
* 标题关键词重叠度
* 正文关键词重叠度
* 来源数
* 命名实体交集（产品名、人物名、金额、地名、机构名）

第一版可行做法：

1. 对去重后的新闻抽取关键词
2. 按时间窗口分桶，例如 3 天内新闻作为一批
3. 对每篇新闻与现有簇计算相似度
4. 若相似度高于阈值，则加入已有簇
5. 否则新建簇

相似度可以先用简单规则：

```text
cluster_score =
0.4 * 标题关键词重叠率 +
0.4 * 正文关键词重叠率 +
0.2 * 命名实体重叠率
```

阈值可先设：

```text
cluster_score >= 0.6 归为同一簇
```

---

### 3.5 事件归并层

职责：

* 把一个聚类簇提升为“事件”
* 将同一事件的多篇新闻整合成统一事件实体

区别：

* 聚类更偏“算法分组”
* 事件归并更偏“业务实体化”

例如同一事件可能包含：

* 路透社首发
* 转载稿
* 评论稿
* 补充背景稿
* 官方回应稿

事件归并后输出一个事件对象，建议包含：

```json
{
  "event_id": "EVT_20260314_001",
  "company_name": "Apple",
  "event_title": "Apple launches new chip and raises performance outlook",
  "event_time_range": {
    "start": "2026-03-13T08:00:00Z",
    "end": "2026-03-14T14:00:00Z"
  },
  "news_ids": ["N1", "N2", "N3"],
  "source_count": 3,
  "top_sources": ["Reuters", "Bloomberg", "CNBC"]
}
```

第一版事件归并策略建议：

* 一个聚类簇先视作一个候选事件
* 若两个簇在以下维度高度接近，则合并为一个事件：

  * 时间窗口重叠
  * 关键词相似
  * 核心实体一致
  * 公司一致
  * 核心动作一致（发布、并购、裁员、诉讼、财报、合作、事故等）

---

### 3.6 LLM 总结层

职责：

* 以事件为单位生成总结
* 不再按新闻逐条总结

输入：

* 一个事件下的多篇去重后新闻
* 事件元信息
* 来源和时间信息

输出：

* 事件摘要
* 关键信息点
* 风险与机会
* 对公司可能的影响

建议输出结构：

```json
{
  "event_summary": "Apple announced a new chip launch, with multiple media sources highlighting improved performance and expected impact on product competitiveness.",
  "key_points": [
    "New chip released",
    "Performance increase highlighted",
    "May improve premium device competitiveness"
  ],
  "market_impact": "Potentially positive for product cycle and margin expectations",
  "confidence": 0.82
}
```

总结提示词建议强调：

* 仅基于输入新闻内容总结
* 不要臆测未出现的信息
* 保留来源间不一致之处
* 明确区分事实与推断
* 输出固定 JSON 结构

---

### 3.7 投资信号提取层

职责：

* 从事件总结中提取投资相关结构化信号
* 用于后续排序、打分、告警、看板展示

推荐输出字段：

```json
{
  "signal_type": "product_launch",
  "sentiment": "positive",
  "impact_direction": "positive",
  "impact_horizon": "short_to_mid",
  "confidence": 0.76,
  "reason": "New product launch may enhance competitiveness and revenue expectations",
  "tags": ["product", "chip", "competitiveness"]
}
```

建议支持的信号类型：

* 财报超预期 / 低于预期
* 产品发布
* 订单增长 / 订单流失
* 产能变化
* 并购 / 战略合作
* 诉讼 / 监管处罚
* 高管变动
* 裁员 / 组织调整
* 安全事故 / 召回
* 供应链风险
* 宏观政策影响
* 市场份额变化
* 舆情负面事件

第一版推荐通过 **规则标签 + LLM 结构化抽取** 结合实现：

1. 先基于关键词做粗分类
2. 再调用 LLM 输出结构化投资信号

这样比完全依赖 LLM 更稳。

## 4. 推荐的 MVP 落地架构

### 4.1 第一版范围

第一版只做以下能力：

* LLM 联网搜索获取公司相关新闻
* 原始新闻标准化
* 文本清洗
* 标题去重
* SimHash 去重
* 基于关键词和时间窗口的简单聚类
* 一个聚类簇对应一个事件
* 事件级 LLM 总结
* 事件级投资信号提取
* 结果落库

### 4.2 暂不纳入第一版的能力

以下能力可以第二阶段再做：

* Embedding 语义聚类
* 跨语言事件合并
* 多公司关联事件图谱
* 新闻可信度评估
* 来源权重建模
* 历史事件演化追踪
* 自动生成事件时间线
* 股票价格联动分析

建议至少设计以下几张表。

用于保存 LLM 搜索返回的原始新闻记录。

```sql
);
```

## 6. 核心处理流程设计

## 6.1 单次任务处理流程

```text
输入公司名
↓
调用 LLM 联网搜索，获取近 N 篇新闻
↓
对每条新闻做标准化与清洗
↓
标题去重
↓
SimHash 去重
↓
保留 unique 新闻
↓
按时间窗口 + 关键词进行聚类
↓
生成事件
↓
调用 LLM 生成事件级总结
↓
调用 LLM 提取投资信号
↓
结构化落库
```

---

## 6.2 去重建议位置

去重位置必须放在：

```text
LLM 联网搜索之后
事件级总结之前
```

即：

```text
搜索 → 去重 → 聚类 → 事件归并 → 总结 → 信号提取 → 落库
```

原因：

* 节省 LLM 成本
* 避免重复总结
* 原始文本更适合做 SimHash
* 事件聚类输入更干净

---

## 7. 文本清洗设计

SimHash 不负责自动清洗，因此文本清洗必须独立实现。

建议清洗内容：

* 去 HTML 标签
* 去 URL
* 去多余空白符
* 去常见模板语句
* 去来源、责任编辑、免责声明等模板字段
* 中英文标点规范化
* 保留标题与正文主体

推荐去重输入文本：

```text
fingerprint_text = clean_title + "\n" + clean_content
```

这样比只用正文更稳。

---

## 8. SimHash 去重实现建议

### 8.1 去重策略

两级策略：

1. 标题标准化精确去重
2. SimHash 近重复去重

### 8.2 SimHash 判定阈值

建议初始阈值：

```text
distance <= 3 判定重复
```

### 8.3 候选集限制

为避免全表扫描，建议只在以下范围比较：

* 同公司
* 最近 7 天或 15 天新闻
* 非重复新闻集合

SQL 候选查询思路：

```sql
SELECT id, simhash_value
FROM raw_news
WHERE company_name = ?
  AND publish_time >= DATE_SUB(NOW(), INTERVAL 7 DAY)
  AND is_duplicate = 0;
```

---

## 9. 聚类设计

第一版不建议一上来用复杂语义聚类，先用规则法。

### 9.1 聚类输入

输入对象：

* 去重后的新闻

输入特征：

* 标题关键词
* 正文关键词
* 命名实体
* 时间窗口
* 来源
* 公司名

### 9.2 聚类规则

可按以下流程实现：

1. 对新闻按发布时间排序
2. 遍历每篇新闻
3. 计算与现有簇的相似度
4. 若存在最高相似簇且超过阈值，则加入簇
5. 否则创建新簇

### 9.3 第一版简化方案

可直接使用：

* 时间窗口：3 天
* 关键词交集比例：>= 0.5
* 标题高频词命中数：>= 2

这版虽然不“高级”，但非常适合 MVP。

---

## 10. 事件归并设计

第一版可采用：

> 一个聚类簇即一个事件

这样最简单，链路也最清晰。

第二版再引入事件合并逻辑，例如：

* 两个簇都提到同一产品发布
* 时间相近
* 实体重叠高
* 动作词一致

则自动归并。

---

## 11. LLM 总结设计

总结建议改为**事件级总结**，不要对单篇新闻逐条总结。

### 11.1 输入

* 事件下所有新闻标题
* 每篇新闻正文或正文片段
* 来源列表
* 时间范围

### 11.2 输出格式

建议固定成 JSON，便于解析：

```json
{
  "event_summary": "",
  "key_points": [],
  "positive_factors": [],
  "negative_factors": [],
  "uncertainties": [],
  "market_impact": "",
  "confidence": 0.0
}
```

### 11.3 Prompt 要求

要求模型：

* 只基于输入内容输出
* 不得补充未出现信息
* 区分事实、媒体表述和推断
* 保留来源之间的不一致信息
* 输出严格 JSON

---

## 12. 投资信号提取设计

建议基于事件级总结做结构化抽取。

### 12.1 输出格式

```json
{
  "signal_type": "",
  "impact_direction": "positive|negative|neutral",
  "impact_horizon": "short|mid|long",
  "sentiment": "positive|negative|neutral",
  "confidence": 0.0,
  "reason": "",
  "risk_level": "low|medium|high",
  "tags": []
}
```

### 12.2 典型标签

* earnings
* product_launch
* partnership
* acquisition
* regulation
* lawsuit
* accident
* supply_chain
* management_change
* capacity
* guidance
* market_share

### 12.3 第一版建议

先做“单事件单信号主标签”即可，不要一开始做太复杂的多信号体系。

## 13. 异常与边界处理

系统需要考虑以下边界情况：

### 13.1 联网搜索返回内容过短

处理方式：

* 若内容不足最小长度，例如 100 字，则标记为低质量新闻
* 不进入聚类和总结环节

### 13.2 搜索结果无正文，只有摘要

处理方式：

* 用标题 + 摘要作为去重和聚类输入
* 标记 `content_type = snippet`

### 13.3 同一新闻多次搜索返回

处理方式：

* 通过 URL hash + 标题去重 + SimHash 多层过滤

### 13.4 新闻数量过多

处理方式：

* 单次搜索先限制最大新闻数，例如 20 或 30
* 优先保留高可信来源
* 再做去重与聚类

## 15. 第一版任务拆解

下面按落地顺序拆解。

### 第一步：定义统一新闻数据结构

要做的事：

* 定义新闻对象字段
* 统一联网搜索返回结构
* 明确哪些字段必填

产出：

* `NewsItem` 数据结构
* 原始新闻表建表 SQL

---

### 第二步：实现新闻标准化与文本清洗

要做的事：

* 去 HTML
* 去 URL
* 去模板字段
* 生成 `clean_title` 和 `clean_content`

产出：

* `clean_text()` 方法
* `normalize_news()` 方法

---

### 第三步：实现标题去重与 URL 去重

要做的事：

* URL 标准化
* title 标准化
* 建立简单精确去重规则

产出：

* `normalize_url()`
* `normalize_title()`
* `is_exact_duplicate()`

---

### 第四步：实现 SimHash 去重

要做的事：

* 对 `title + content` 生成 SimHash
* 查询近 7 天候选文章
* 计算 Hamming Distance
* 标记重复新闻

产出：

* `calc_simhash()`
* `find_duplicate_news()`

---

### 第五步：实现新闻聚类

要做的事：

* 设计聚类相似度规则
* 按时间窗口聚类
* 生成簇对象

产出：

* `cluster_news(news_list)`
* 聚类表与关联表

## 16. 推荐的第一版结论

对于你当前这个系统，推荐采用如下最小可行架构：

```text
公司名
↓
LLM 联网搜索新闻
↓
文本清洗
↓
标题去重 + SimHash 去重
↓
基于时间窗口和关键词聚类
↓
一个聚类簇生成一个事件
↓
LLM 生成事件级总结
↓
LLM 提取投资信号
↓
结构化落库
```

该方案的优点是：

* 能明显减少重复新闻
* 能减少大模型调用次数
* 能把“新闻”提升为“事件”
* 能为后续投资分析提供更稳定的输入
* 架构简单，适合快速实现 MVP
* 后续可以自然扩展到 embedding、向量检索、事件图谱等能力
